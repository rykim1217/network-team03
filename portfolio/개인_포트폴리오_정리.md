## 1. 설치와 실행

### 사전 조건

- Windows 10/11 또는 VM
- Git, Docker Desktop, Python 3.13 이상
- MySQL, Graylog, Wazuh, n8n이 실행 가능한 환경
- 시나리오 3 네트워크 차단까지 재현할 때는 pfSense VM과 설정된 방화벽 별칭

### 실행 순서

```powershell
git clone https://github.com/rykim1217/network-team03.git
cd network-team03
Copy-Item .env.example .env
# .env에 로컬 Middleware 수집 키만 입력
python -m pip install -r requirements.txt -r web-app/requirements.txt

# MySQL·미들웨어·Graylog·Wazuh·n8n을 먼저 실행한 뒤
.\start-enginesquare.ps1
```

주요 주소는 API `5000`, 웹·대시보드 `5001`, Middleware ingestor `8000`, worker metrics `9100`, Graylog `9000`/GELF `12201`, n8n `5678`입니다. pfSense는 `https://172.16.50.2`이며 시나리오 3의 실제 네트워크 차단을 확인할 때만 필요합니다.

### 설정 파일

- Graylog: `scenario*/graylog/`의 스트림·집계·알림 규칙
- Wazuh: `scenario2-api-key-compromised/wazuh/`
- n8n: 각 시나리오의 JSON 워크플로우
- 로컬 비밀값: `.env`와 n8n 화면에만 입력
- 저장소에는 실제 키·토큰·Discord 웹훅 URL을 넣지 않고 `.env.example`과 placeholder를 사용

## 2. 전체 동작 흐름

공격 이벤트 발생 → API/미들웨어 수집 → SQLite WAL 버퍼링 → Graylog/Wazuh 탐지 → n8n 자동 대응 → API·대시보드·Discord·pfSense 반영 → 차단 해제 또는 키 재발급으로 복구하는 구조입니다.

- API health, 웹 접속, Graylog 알림, n8n 실행, 시나리오 1 브루트포스, 시나리오 3 CRITICAL/WARNING, 2만 건 스파이크를 개인 PC에서 재현

## 4. 시나리오별 실행과 실측 결과

### 시나리오 1: 브루트포스 자동 대응

```powershell
python scenario1-middleware\simulators\demo_bruteforce_attack.py --ip 198.51.100.80 --count 5
```

동일 IP의 401 실패를 발생시키고 Graylog 집계 → n8n → `/automation/revoke-key` → IP 차단 순서로 확인했습니다. Graylog에 `[S1] Brute Force Attack Detection`이 발생했고, n8n 실행은 성공했으며, 테스트 IP는 차단 목록에 반영된 뒤 정리했습니다.

### 시나리오 1: 2만 건 스파이크

```powershell
python scenario1-middleware\simulators\spike_test_demo.py --spike-count 20000
```

최종 metrics는 `received=20,005`, `forwarded=20,005`, `dropped=0`, `DLQ=0`, `queue lag=0`이었습니다. 스크립트의 엄격한 수량 비교는 실행 중 발생한 백그라운드 이벤트 1건 때문에 `sent=20,004` 대 `received=20,005`로 실패했지만, 최종 파이프라인은 0건 유실로 drain됐습니다. 이 차이를 숨기지 않고 검증 기록에 남겼습니다.

### 시나리오 2: 유출 API 키 대응

```powershell
# n8n 편집기에서 Scenario 2 - API Key Compromised Response를 직접 실행
# 또는 저장소의 시나리오 2 재현 절차에 따라 비허용 IP 요청 발생
```

n8n에서 직접 실행한 워크플로우는 정상 진행되어 키 폐기·재발급, 공격자 IP 차단, 인시던트·대시보드·Discord 노드까지 확인했습니다. 별도로 Graylog에서 운영용 production webhook을 호출할 때 `POST /webhook/scenario2-api-key-compromised` 404가 한 번 관찰되어, 실제 제출 전에는 n8n 활성화 상태와 Graylog URL을 다시 확인해야 합니다. 수동 실행 성공을 자동 연동 성공으로 과장하지 않았습니다.

### 시나리오 3: 킬체인 상관분석

```powershell
python scenario3-killchain\scripts\test_killchain.py critical
python scenario3-killchain\scripts\test_killchain.py warning
```

- CRITICAL: 정찰·API 키 침해·장비 제어 3단계를 같은 IP로 전송하고, Graylog 상관분석 → n8n → pfSense 차단 별칭·인시던트 등록까지 확인했습니다.
- WARNING: 1~2단계만 전송했을 때 CRITICAL로 격상되지 않고 경고 수준으로 남는 오탐 방지 동작을 확인했습니다.
- 복구: pfSense 차단 별칭에서 테스트 IP를 제거하는 수동 승인 절차를 사용합니다.

## 5. 문제점 → 원인 → 해결 → 결과

### Middleware `/metrics` 응답 지연

- 문제점: 2만 건 테스트 첫 실행 전에 `/metrics`가 응답하지 않았습니다.
- 원인: ingestor/worker 컨테이너의 실행 상태가 비정상이고 WAL 처리가 정체됐습니다.
- 해결: `soar-http-ingestor`, `soar-consumer-worker`를 재시작하고 `/health`와 `/metrics`를 재확인했습니다. WAL은 보존했습니다.
- 결과: 재실행 후 queue lag가 0으로 내려갔고, 최종 metrics에서 유실·DLQ가 0임을 확인했습니다.

### Discord 알림 방식 불일치

- 문제점: 기존 워크플로우에 팀 공용 봇 방식과 실제 개인 채널 설정이 섞여 있었습니다.
- 원인: n8n Discord 노드가 봇 REST API와 웹훅 입력을 혼용했습니다.
- 해결: Incoming Webhook 방식으로 통일하고 저장소 JSON에는 placeholder만 남겼습니다.
- 결과: 활성 n8n 워크플로우의 Discord 알림 대상을 개인 채널로 교체했고, 저장소에서 실제 웹훅과 구형 봇 토큰을 제거했습니다.

### 시나리오 2 production webhook 404

- 문제점: n8n 편집기 직접 실행은 성공하지만 Graylog 호출은 404였습니다.
- 원인 후보: n8n의 운영 웹훅 활성화 상태 또는 Graylog에 저장된 경로가 현재 워크플로우 상태와 일치하지 않습니다.
- 해결 계획: 워크플로우를 Publish/Active 상태로 확인하고, Webhook 노드 path와 Graylog 알림 URL을 동일하게 맞춘 뒤 비허용 IP 이벤트로 재검증합니다.
- 현재 결과: 수동 실행은 성공, Graylog 자동 호출은 최종 확인 대기입니다.

## 6. 개선점과 느낀 점

대량 로그를 단순히 Graylog로 바로 보내는 방식은 하위 시스템 장애 시 재시도와 유실 검증이 어렵습니다. WAL, 속도 제한, 선별 재시도를 넣으면서 수집과 분석을 분리하는 이유를 확인했습니다. 또 자동화는 “워크플로우가 저장되어 있다”만으로 충분하지 않고, 실제 production webhook·대시보드·외부 알림까지 끝까지 확인해야 한다는 점을 배웠습니다.

발표 이후에는 Discord 알림을 개인 채널로 정리하고 실제 주소를 저장소에서 제거했으며, 2만 건 실측과 시나리오 3의 WARNING 오탐 방지 검증을 추가했습니다. 시간이 더 있다면 시나리오 2 production webhook smoke test를 자동화하고, 2만 건 테스트가 백그라운드 이벤트와 섞이지 않도록 run id를 도입하겠습니다.
